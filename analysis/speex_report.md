# Speex 帧结构、激励/合成参数与模式切换验证

## 结论摘要

- Speex 的 NB/WB/UWB 分别对应 8/16/32 kHz、20 ms 帧：160/320/640 个全带样点。
- WB/UWB 是嵌入式分层位流。每个包先放 NB 层，再以 1 bit 宽带标志加 3 bit 子模继续附加高频层；UWB 在 WB 层之后再加一层。
- VAD 不在包内。VAD 只控制编码器是否进入 DTX/静音子模；解码器从位流的层标志和子模推断帧类型。48/48 个 NB、WB、UWB 包全部推断正确。
- 每帧由 4 个子帧组成。子帧是时间单位；码本索引是子帧内创新矢量的量化索引。宽带高频子帧还带增益索引、5 个 shape 索引和 5 个符号位。
- 内置确定性语音样例重建包络相关为 0.9915/0.9962/0.9986；残差包络相关为 0.9778/0.9807/0.9845。
- WB 在同一编解码器内执行 `quality 8 -> 10 -> 8` 切换，边界归一化频带距离为 1.1668/2.3672 dB，常态中位数为 1.3329 dB；没有出现离群频谱断崖。
- Speex 本身没有独立的 pre-emphasis 状态，使用高通记忆与 LPC 合成记忆。NB 解码后的高通状态确为非零；切换到新建 WB 解码器后，低带高通、LPC 和 QMF 记忆全部为零。

完整机器可读输出在 `artifacts/speex_probe.json`，包含每个代表子帧的激励样点、LPC、增益、`pi_gain`、残差能量和完整码本索引。

## 1. 帧模式与位流

| 模式 | 采样率 | 帧长 | 顶层结构 | 子帧 | LPC 阶数 |
|---|---:|---:|---|---:|---:|
| NB (`SPEEX_MODEID_NB=0`) | 8 kHz | 160 | 1 bit 零 + 4 bit NB 子模 + 数据 | 4 x 40 | 10 |
| WB (`SPEEX_MODEID_WB=1`) | 16 kHz | 320 | NB 层 + 1 bit 宽带标志 + 3 bit WB 子模 + 高频数据 | 低带 4 x 40；高带 4 x 40 | 低带 10；高带 8 |
| UWB (`SPEEX_MODEID_UWB=2`) | 32 kHz | 640 | NB 层 + WB 层 + 1 bit 宽带标志 + 3 bit UWB 子模 + 更高频数据 | 低带 4 x 40；WB 高带 4 x 40；UWB 高带 4 x 80 | 低带 10；高带 8 |

这里的“帧类型”不是包长猜出来的。NB 编码器即使在 WB/UWB 中也会先在包首写 `0` 和 NB 子模；随后 WB/UWB 层才是带 `1` 标志的附加块。因此正确分类必须按 `bits_per_frame` 跳过前一层的完整数据，而不能只看首 bit。

VAD/DTX 是编码器控制量。关闭 VAD 后，位流没有专门的 VAD 字段；本次所有运行均设置 `SPEEX_SET_VAD=0`，分类仍完全正确。DTX 静音则由 NB 子模及特定增益状态表达，不由一个外部 VAD 位解码。

## 2. 子帧与码本

一个 20 ms 帧含 4 个子帧。每个子帧分别传输：

1. 子帧增益索引或全局增益/增益修正；
2. LTP/基音参数（NB 的语音类子模）；
3. 创新码本索引，通常拆成多个 shape 子矢量；
4. 含符号的宽带高频码本额外有符号位。

本次代表帧的实际布局：

| 层 | 子模 | 子帧 | 每子帧码本结构 | 码本比特 |
|---|---:|---:|---|---:|
| NB 低带 | 5 | 4 x 40 | 8 个 shape 索引，每索引 6 bit，无符号位；另有 3 bit 增益索引 | 48 |
| WB 低带 | 6 | 4 x 40 | 8 个 shape 索引，每索引 8 bit，无符号位；另有 3 bit 增益索引 | 64 |
| WB 高带 | 3 | 4 x 40 | 5 个索引，每索引 7 bit + 1 个符号位；另有 4 bit 增益索引 | 40 |
| UWB 高带 | 1 | 4 x 80 | 无 split-codebook；每子帧 5 bit 频谱折叠增益 | 5 |

因此，“第 2 子帧的第 1 个码本索引”是二维定位，不是把子帧号当索引。JSON 中每项为：

```text
frames -> layers -> subframes -> codebooks -> gain_index / indices / signs
```

## 3. 包络与残差

样例由程序内置生成，使用确定性谐波、共振峰和音节包络；幅度按 int16 量化输入。每种模式 48 帧，质量 8，VAD、DTX、VBR、高通和 LPC 增强均关闭，避免后处理掩盖核心残差。

| 模式 | 平均包比特 | 类型推断 | 包络相关 | 包络 NRMSE | 残差包络相关 | 帧延时 |
|---|---:|---|---:|---:|---:|---:|
| NB | 300 | 48/48 | 0.991547 | 0.085005 | 0.977771 | 1 帧 |
| WB | 556 | 48/48 | 0.996177 | 0.058031 | 0.980657 | 1 帧 |
| UWB | 592 | 48/48 | 0.998550 | 0.045854 | 0.984453 | 1 帧 |

包络 NRMSE 是帧 RMS 序列按最佳帧延时对齐后的相对误差。UWB 改善来自额外高频层，但也意味着它并非“更干净的 NB”，而是分层给全带增加 8–16 kHz 内容。

## 4. 宽带子模切换频谱

为避免信号内容本身变化，切换测试连续输入同一个 16 kHz 稳态宽带样例，使用同一个 WB 编码器和解码器：

- 第 0–19 帧：quality 8（profile 包 556 bit）；
- 第 20–39 帧：quality 10（profile 包 844 bit）；
- 第 40–63 帧：quality 8。

每帧做 Hann 窗 DFT，汇总为 16 个归一化对数频带能量。频谱距离为相邻帧去均值频带 dB 差的 RMS。

| 指标 | 数值 |
|---|---:|
| 常态相邻帧 LSD 中位数 | 1.332902 dB |
| `8 -> 10` 边界（第 20 帧） | 1.166824 dB |
| `10 -> 8` 边界（第 40 帧） | 2.367168 dB |
| 4–8 kHz 能量占比，第 19/20 帧 | 3.3667% / 3.8138% |
| 4–8 kHz 能量占比，第 39/40 帧 | 4.1112% / 3.6547% |

两个边界都没有 LSD 尖峰；高频占比只发生约 11%–13% 的档位变化，没有跌到零，也没有阶跃式断崖。因此“宽带档位切换时频谱无断崖”成立。这里的切换通过每帧重写 `submodeID` 完成，没有重建解码器，也没有清空 QMF/LPC 状态。

## 5. NB -> WB 状态重置

需要先纠正术语：官方 Speex CELP 路径没有独立的 pre-emphasis 滤波器，也没有 `preemph_mem` 字段。最接近且实际影响边界连续性的状态是：

- 低带解码器 `DecState.mem_hp[2]`：高通记忆；
- 低带 `DecState.mem_sp[10]` 与高带 `SBDecState.mem_sp[16]`：LPC 合成记忆；
- `SBDecState.g0_mem/g1_mem[64]`：QMF 合成记忆。

实验中先让 NB 解码器处理一帧，旧 NB 高通状态为非零。随后按正确方式销毁 NB 解码器并初始化 WB 解码器，检查结果：

| 检查项 | 结果 |
|---|---|
| 旧 NB 高通记忆非零 | true |
| 新 WB 低带高通记忆为零 | true |
| 新 WB 低带/高带 LPC 记忆为零 | true |
| 新 WB QMF 记忆为零 | true |
| 等价状态重置确认 | true |

注意：官方 `SPEEX_RESET_STATE` 的 NB 解码器分支只清 `mem_sp` 和激励缓冲，并不清 `mem_hp`。因此不应把“复用同一个 NB 状态并改一个 wideband 标志”当作完整模式切换。本验证使用新建 WB 编解码器实例，这是 Speex 分层 API 下的正确模式切换方式；如果应用复用实例，应额外清高通状态，或显式分配全新的编解码器。

## 6. 复现

```bash
bash scripts/build_probe.sh
```

脚本会：

1. 拉取固定提交 `09b569d1b437e5edccf3406a38714ad795e46d38` 的官方 Speex；
2. 以浮点模式直接编译库和探针；
3. 通过 `--wrap` 截获 `lsp_to_lpc`、`iir_mem16` 与 split-codebook 反量化，不修改 Speex 源码；
4. 写入 `artifacts/speex_probe.json`。

验证命令：

```bash
cc -std=c99 -Wall -Wextra -Wpedantic -DHAVE_CONFIG_H \
  -Icompat -Icompat/speex \
  -I.build/speex-1.2.1/include -I.build/speex-1.2.1/libspeex \
  -fsyntax-only src/speex_probe.c
python3 -m json.tool artifacts/speex_probe.json >/dev/null
```

另外用 `-fsanitize=address,undefined` 构建并运行，未报告内存或未定义行为问题，且 sanitizer 输出与普通构建逐字节一致。
